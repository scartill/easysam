# Specification Critique Report: CloudFormation Support for DynamoDB Vector Indexes

- **Target Spec**: `docs/specs/vector-indices.md`
- **Target Revision**: `ac43149b4c059fc98d2a0e1430da21493ac4e784`
- **Date**: 2026-11-07
- **Verdict**: ⚠️ **PROCEED WITH UPDATES**

---

## Executive Summary

The specification `docs/specs/vector-indices.md` provides a well-structured and concise design for consuming Prismarine's `vectorindices` table block and rendering AWS native `AWS::DynamoDB::Table VectorIndexes` along with scoped `dynamodb:SearchVectors` IAM policies. Adopting the hybrid architectural split (Approach C: Python-level attribute injection and deduplication in `load.py`, coupled with template rendering and policy derivation in `template.j2`) aligns directly with EasySAM's established design patterns.

However, an adversarial product and engineering review revealed **three Must-Address technical defects** and several **high-value recommendations** that must be resolved before task breakdown:
1. **CloudFormation / DynamoDB Vector Search Incompatibility (E1)**: The spec allows `filters` without `hash`, which will emit a `SearchSchema` lacking a `HASH` element. AWS DynamoDB rejects any `SearchSchema` that does not declare a partition key `HASH` element.
2. **Jinja2 Runtime Crash on Null/Undefined Function Tables (E2)**: The IAM template snippet does not defensively guard against functions with missing or `null` `tables` definitions, causing Jinja2 to raise `TypeError: argument of type 'NoneType' is not iterable` during template rendering.
3. **Flawed Deduplication Scope for `AttributeDefinitions` (E3)**: Collecting existing attributes from GSI `indices` during deduplication causes attributes that appear in GSI key schemas but not in `table.attributes` to be falsely marked as already present, omitting them from `AttributeDefinitions` and triggering CloudFormation validation failures.

Resolving these issues will make the specification technically watertight and ready for `Split Tasks`.

## Product Lens Findings

### 1a. Problem Validation
- **Pain Point & Value**: EasySAM currently drops the `vectorindices` block generated by Prismarine. Supporting native DynamoDB vector indexes is high leverage because DynamoDB native vector search removes the need for auxiliary vector search infrastructure (such as OpenSearch Serverless / AOSS) for light to medium semantic search workloads.
- **Scope Boundary**: Confining EasySAM's scope to template synthesis and IAM policy provisioning while leaving runtime search execution and embedding generation to client code is appropriate and respects architectural boundaries.

### 1b. User Value Assessment
- **P1 (💡 Recommendation — User Value)**: *Undocumented path for numeric and binary filter attributes.*
  - *Finding*: The spec designates numeric/binary filter types as "Out of Scope" and states injected attributes default to `S`. However, DynamoDB natively supports `N` and `B` types for vector index partition keys and inline filters. Because EasySAM's deduplication logic checks `table.attributes` first, a developer who manually declares `table.attributes: [{name: price, type: N}]` can actually use numeric filters today without code changes. Stating that numeric filters are out of scope without documenting this workaround misleads users into believing numeric filtering is entirely unsupported.
  - *Suggestion*: Document clearly in the spec and user documentation that while automatically injected schema attributes default to `S`, users can specify `type: N` or `type: B` by pre-declaring the attribute in `table.attributes`.

### 1c. Alternative Approaches
- **Approach Selection**: Approach C (Hybrid) is superior to Approach A (template-only) and Approach B (heavy preprocessing). Performing deduplication in Python where set arithmetic is trivial, while keeping IAM and resource synthesis in Jinja2 where precedents already exist (such as DynamoDB streams), minimizes codebase churn.

### 1d. Edge Cases & User Experience
- **P2 (💡 Recommendation — Operational Migration Guidance)**: *CloudFormation update limitation when adding vector indexes to existing tables.*
  - *Finding*: CloudFormation permits only one index change (GSI or vector index) per single stack operation. Adding a vector index to an existing table that already has GSIs, or adding multiple vector indexes simultaneously to an existing stack, will cause `sam deploy` to fail. While this is captured as a "documented caveat," the spec lacks clear procedural guidance for developers on how to sequence stack updates during migrations.
  - *Suggestion*: In the documentation follow-up (Task 7), detail the exact operational migration steps: deploy one index per stack operation when updating active stacks, and note that initial table creation (`CreateTable`) allows multiple indexes simultaneously.

### 1e. Success Measurement
- **P3 (🤔 Question — Integration Verification)**: *Verifying end-to-end parity with Prismarine's actual emitted structure.*
  - *Finding*: The spec specifies a hermetic example using a literal `tables:` block in `example/vectorindices/` so EasySAM's CI remains self-contained. However, Seed Q6 calls for coordinated release with Prismarine.
  - *Question*: What is the concrete verification checkpoint to test that the dictionary emitted by `prisma_easysam.build_dynamo_tables` is accepted without schema errors or key-mapping discrepancies before publishing?

## Engineering Lens Findings

### 2a. Architecture Soundness
- **E1 (🎯 Must-Address — Architecture Soundness)**: *Invalid `SearchSchema` rendered when `filters` is declared without `hash`.*
  - *Finding*: In DynamoDB native vector search, an index partition key (`HASH`) is required whenever a `SearchSchema` is defined. Inline filters (`INLINE_FILTER`) cannot exist on their own without a `HASH` element. The spec allows `hash` and `filters` to be independently optional in schema definition (R1) and renders `SearchSchema` if `vindex.hash or vindex.filters` (R2, line 198). If a table defines `filters` without `hash`, EasySAM will emit:
    ```yaml
    SearchSchema:
      - AttributeName: myfilter
        SearchSchemaElementType: INLINE_FILTER
    ```
    CloudFormation and DynamoDB will reject this template at deployment time with `ValidationException`.
  - *Suggestion*: Update the schema in `schemas.json` and `local_schemas.json` to enforce that `filters` requires `hash` (via JSON Schema Draft 7 `"dependencies": {"filters": ["hash"]}`). In addition, validate in `load.py` or `validate_schema.py` that any vector index with `filters` also defines `hash`.

- **E2 (🎯 Must-Address — Failure Modes)**: *Jinja2 runtime crash when function `tables` is missing or `null`.*
  - *Finding*: The proposed IAM policy snippet in `template.j2` (line 221) uses:
    ```jinja
    {% if table.vectorindices and table_name in function.tables %}
    ```
    In `resources.yaml`, functions are not required to define `tables`. If a function defines no `tables` or defines `tables: null` (a common YAML idiom for empty fields), evaluating `table_name in function.tables` in Jinja2 raises `TypeError: argument of type 'NoneType' is not iterable`, crashing the template generator.
  - *Suggestion*: Guard the membership check defensively:
    ```jinja
    {% if function.tables and table.vectorindices and table_name in function.tables %}
    ```

- **E3 (🎯 Must-Address — Implementation Flaw)**: *Incorrect deduplication scope across `indices` and `table.attributes`.*
  - *Finding*: Proposed Solution 2 states:
    > "collect existing attribute names (`table['attributes']` plus any GSI `indices[].attributes[].name`); for each index's `hash` and each `filters` entry, if the name is not already present, append `{'name': <attr>}` to `table['attributes']`"
    
    In EasySAM, `template.j2` renders `AttributeDefinitions` solely by looping over `table.attributes` (lines 413–421). It does not loop over `indices`. If an attribute name exists in a GSI's `attributes` block but not in `table.attributes`, the spec's logic treats it as "already present" and fails to append it to `table.attributes`. Consequently, that attribute is omitted from `AttributeDefinitions`, and CloudFormation rejects the template because every `SearchSchema` attribute must appear in `AttributeDefinitions`.
  - *Suggestion*: Base the deduplication check exclusively on `table.get('attributes', [])`. Furthermore, ensure the set of known attributes is updated in-memory as each vector index is processed, ensuring duplicate filter/hash attributes across multiple vector indexes on the same table are not injected multiple times.

### 2b. Failure Mode Analysis
- **E4 (💡 Recommendation — Validation Gap)**: *CloudFormation VectorIndex naming and array constraints unenforced in schema.*
  - *Finding*: CloudFormation enforces strict naming and quota constraints on `VectorIndexes`:
    1. `IndexName`: length between 3 and 255 characters, matching regex `^[a-zA-Z0-9_.-]+$`.
    2. Vector indexes per table: maximum 5.
    3. Inline filters per index: maximum 18.
    The spec's proposed `vector_index_schema` defines `"name": {"type": "string"}` and unbounded `vectorindices` and `filters` arrays. Malformed index names (e.g., containing spaces, symbols, or fewer than 3 characters) or excessive index declarations will pass EasySAM validation and fail only after CloudFormation initiation.
  - *Suggestion*: Add `"pattern": "^[a-zA-Z0-9_.-]+$"`, `"minLength": 3`, `"maxLength": 255` to the `name` property, `"maxItems": 5` to `vectorindices`, and `"maxItems": 18` to `filters` in both schema files.

- **E6 (💡 Recommendation — Schema Validation)**: *Missing validation for collision between `attribute` and `SearchSchema`.*
  - *Finding*: In DynamoDB vector search, the vector attribute (holding the float embedding array) cannot also be used as the `HASH` partition key or an `INLINE_FILTER`. If a user accidentally specifies the same attribute for both `attribute` and `hash` or `filters`, EasySAM will inject the embedding attribute into `AttributeDefinitions` with `AttributeType: S`, leading to CloudFormation or runtime write errors.
  - *Suggestion*: Add validation in `validate_schema.py` ensuring `vindex['attribute'] != vindex.get('hash')` and `vindex['attribute'] not in vindex.get('filters', [])`.

### 2c. Security & Privacy Review
- **IAM Least Privilege**: Scoping `dynamodb:SearchVectors` to the index ARN (`${TableLogicalId.Arn}/index/${IndexName}`) rather than the table ARN (`${TableLogicalId.Arn}`) or wildcard `*` adheres to the principle of least privilege.
- **E5 (💡 Recommendation — Operational Sizing)**: *Consolidate IAM policy statements to conserve IAM role limits.*
  - *Finding*: The proposed template emits a full `- Version: "2012-10-17"` policy document for *every* vector index individually. If a function references two tables each having two vector indexes, four separate policy documents are injected into the function's SAM role. IAM roles have strict size quotas (max 10,240 characters for inline policies).
  - *Suggestion*: Consolidate all vector index ARNs for a table into a single `Resource` list under one statement, or combine them across tables into a single policy document.

### 2d. Performance & Scalability
- Vector indexes in DynamoDB require on-demand billing mode (`PAY_PER_REQUEST`). EasySAM already hardcodes `BillingMode: PAY_PER_REQUEST` in `template.j2`, ensuring this prerequisite is met without changes.

### 2e. Testing Strategy
- **E7 (💡 Recommendation — Verification Scope)**: *Gaps in test matrix for edge cases.*
  - *Finding*: While the spec's testing strategy covers basic happy paths, byte-identical baseline, and basic invalid inputs, it lacks test cases for:
    1. Functions with no `tables` property (or `tables: null`) alongside vector tables (verifying fix for E2).
    2. Multiple vector indexes on the same table sharing identical filter attributes (verifying fix for E3).
    3. Rejection of `filters` without `hash` (verifying fix for E1).
    4. Optional validation check via `sam validate` to ensure generated templates pass SAM CLI parser rules.
  - *Suggestion*: Explicitly include these specific test cases in the `Testing & Risk Strategy` and Task 6.

### 2f. Operational Readiness
- Handled properly via documentation caveats (CloudFormation single index update per stack operation).

### 2g. Dependencies & Integration Risks
- Hermetic example app without a hard runtime dependency on Prismarine in CI preserves test isolation while allowing Prismarine and EasySAM to be version-bumped and released concurrently.

## Cross-Lens Insights

### Index Validation vs. Deployment Latency (Usability × Reliability)
Both Product and Engineering lenses identify that catching invalid DynamoDB Vector Search configurations (such as inline filters without a partition key, malformed index names, or exceeding the 5-index limit) at generation time rather than deployment time is essential. CloudFormation DynamoDB deployments take several minutes to roll back upon failure. Enforcing strict JSON schema constraints and pre-generation validation saves developer time and prevents deployment lockups.

## Verdict

### ⚠️ PROCEED WITH UPDATES

The specification provides a solid hybrid design for DynamoDB Vector Search support in EasySAM. Addressing the three Must-Address items (**E1**, **E2**, and **E3**) and incorporating the recommended schema constraints and test cases will ensure an error-free implementation.

---

## Remediation Suggestions

Specific recommended edits to `docs/specs/vector-indices.md`:

1. **Section: Requirements (R1 & R2)**
   - Amend R1: Declare that `filters` requires `hash` to be specified; specify `name` pattern `[a-zA-Z0-9_.-]+` (len 3..255), and max 5 vector indexes per table.
   - Amend R2: Note that `SearchSchema` is emitted only when `hash` is present, with `filters` mapped to `INLINE_FILTER`.

2. **Section: Proposed Solution (Items 1, 2, 3, 4)**
   - **Item 1 (Schema)**: Add `"pattern": "^[a-zA-Z0-9_.-]+$"`, `"minLength": 3`, `"maxLength": 255` on `name`, `"dependencies": {"filters": ["hash"]}`, `"maxItems": 5` on `vectorindices`, and `"maxItems": 18` on `filters`.
   - **Item 2 (Preprocessing)**: Change deduplication collection to inspect only `table.get('attributes', [])`, updating `seen_attributes` across all vector indexes on the table.
   - **Item 4 (IAM Template)**: Update condition to `{% if function.tables and table.vectorindices and table_name in function.tables %}`, and consolidate index ARNs under a single policy document.

3. **Section: Testing & Risk Strategy**
   - Add test cases verifying: (a) function with `tables: null` does not crash Jinja, (b) multiple vector indexes on one table deduplicate shared filter attributes in `AttributeDefinitions`, (c) rejection of `filters` without `hash`.
